# Задача: CRM для автосервиса (СТО)

Сделай веб-приложение для управления небольшим автосервисом. Пользователей двое: владелец (полный доступ, контроль) и менеджер (работа с клиентами, заказ-нарядами). Приложение должно запускаться локально на одном компьютере в СТО, но архитектура должна позволять без переделок задеплоить это же приложение на обычный хостинг.

## Стек
- Backend: FastAPI (Python)
- БД: SQLite через SQLAlchemy (ORM обязательно, не сырой SQL — понадобится безболезненная миграция на Postgres в будущем)
- Frontend: простой React (без лишних библиотек) ИЛИ обычный HTML+JS, если так будет проще и легче — на твоё усмотрение, критично только чтобы было просто поддерживать одному человеку
- Авторизация: простой логин/пароль, два аккаунта с ролями `owner` и `manager` (хранить хэш пароля, не plain text)

## Модель данных

**clients**
- id, full_name, phone (формат +7XXXXXXXXXX, нормализуй при сохранении), email (опц.), comment

**vehicles**
- id, client_id (FK), brand, model, plate_number, vin, year

**orders** (заказ-наряды)
- id, vehicle_id (FK), client_id (FK), created_at, status (enum: new / in_progress / done / issued / paid), total_amount, comment

**services** (справочник типовых работ — нужен, чтобы потом надёжно фильтровать отчёты по виду работ)
- id, name (напр. "Замена тормозных колодок"), category (опц., напр. "Тормозная система")

**service_prices** (справочник цен на работы, с гибкой привязкой к авто)
- id, service_id (FK), brand (nullable), model (nullable), price
- Логика: `brand`/`model` не обязательны. Возможные варианты одной и той же услуги:
  - и brand, и model заполнены → цена именно под эту марку+модель (например, "Замена колодок" для Toyota Camry — 5000₽)
  - заполнен только brand → цена для всех моделей этой марки (Toyota — 4000₽)
  - оба поля пустые → общая цена для всех авто (по умолчанию 3000₽)
- При выборе услуги в заказ-наряде для конкретного авто система ищет цену по приоритету: точное совпадение (brand+model) → совпадение только по brand → общая цена (brand и model = null). Если ничего не найдено — поле цены остаётся пустым, менеджер вводит вручную.
- На уровне БД: уникальность по (service_id, brand, model), чтобы не было дублей одного и того же правила

**order_items** (позиции работ внутри заказ-наряда)
- id, order_id (FK), service_id (FK на services, nullable), work_name (свободный текст — если работы нет в справочнике, вбивается вручную), employee_id (FK, исполнитель), price, status (enum: pending / in_progress / done)

**order_parts** (запчасти, использованные в заказ-наряде)
- id, order_id (FK), part_name, article (артикул, опц.), quantity, price_per_unit, total_price (quantity * price_per_unit)

**employees**
- id, full_name, role (mechanic / manager), rate_type (fixed / percent), rate_value

**status_history** (опционально, но сделай сразу — полезно для аналитики)
- id, order_id (FK), status, changed_at

## Функционал MVP
1. CRUD клиентов + привязанных к ним авто
2. Простой раздел "Справочник работ и цен": добавление/редактирование услуг (services) и правил цены (service_prices) — с формой, где марка и модель авто не обязательны для заполнения
3. Создание заказ-наряда: выбор клиента/авто, добавление позиций работ с назначением исполнителя. При выборе услуги из справочника — цена подставляется автоматически по логике выше (можно вручную скорректировать)
4. В рамках заказ-наряда — добавление использованных запчастей (название, артикул опционально, количество, цена за единицу). Итоговая сумма заказ-наряда (`total_amount`) считается автоматически как сумма всех работ (order_items) + сумма всех запчастей (order_parts)
5. Смена статуса заказ-наряда и отдельных позиций работ (с записью в status_history)
6. Список заказ-нарядов с фильтрами по статусу / дате / клиенту
7. Простая карточка сотрудника: список назначенных на него работ и сумма (для будущего расчёта зарплаты)
8. Разграничение: manager видит и редактирует клиентов/заказ-наряды; owner дополнительно видит сводную аналитику (количество заказов, сумма за период, загрузка по сотрудникам)

## Отчётность (важный блок, сделать гибко)

Раздел "Отчёты" с двумя видами отчётов:

**А. Детальный отчёт по заказ-нарядам**
Таблица со строкой на каждый выполненный заказ-наряд (или на каждую позицию работы — сделай переключатель вида "по заказам" / "по работам"), со столбцами: дата, клиент (имя+телефон), авто (марка/модель/гос.номер), перечень выполненных работ, кто выполнял (исполнитель), запчасти, итоговая сумма, статус.

Фильтры (должны комбинироваться друг с другом):
- диапазон дат (от/до)
- клиент (поиск по имени/телефону)
- сотрудник-исполнитель
- статус заказа
- вид работы — по `service_id` из справочника services (плюс опционально текстовый поиск по `work_name`, если работа не из справочника)

Результат отчёта: возможность посмотреть в интерфейсе + выгрузить в CSV/Excel.

**Б. Отчёт "клиенты по виду работ" (для повторных касаний/маркетинга)**
Отдельный, упрощённый режим отчёта: выбираешь одну или несколько услуг из справочника services (например "Замена тормозных колодок") + опционально диапазон дат — получаешь **уникальный список клиентов**, которым эта работа выполнялась, с колонками: имя, телефон, дата последнего выполнения этой работы, авто, сколько раз делали эту работу за всё время.
Такой список должен легко выгружаться в CSV — чтобы дальше можно было обзванивать/писать в WhatsApp/делать рассылку по нему (в будущем — через ту же интеграцию GreenAPI).

Технически: держи это как отдельный API-эндпоинт с параметрами фильтра (service_ids[], date_from, date_to), который делает JOIN orders → order_items → clients и группирует по client_id.
